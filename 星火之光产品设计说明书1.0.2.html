3

TRACK · 天级自动监测（整合 Answerbit）

配置追踪范围→ 🟢 天级并行采样→ 🟢 首份报告 <5min→ 🟢 波动告警→ 历史时间序列

🟢 M15 · 自动监测调度器（新增）

  • 调度：基于 jobs.py 扩展 scheduler，按 geo.json.monitor.freq（默认 daily）并行触发各平台采样，复用现有 sample_platform。
  • 首报时延：onboard 完成后自动开跑首份采样，多数品牌 <5 分钟产出首份可见度报告。
  • 波动告警：对比上一周期，提及率/排名/引用数波动超阈值（默认 ±20%）生成告警，推送至协作看板与（可选）Webhook。
  • 归档：每次采样写入 metrics/<date>.json，自然形成时间序列，支撑趋势与分组视图。

🟡 M4 · 采样升级为持续追踪（增强）

  • 新增 continuous 模式：采样不仅产出当前快照，还写入"品牌提及率/平均排名"逐日序列，供趋势图直接消费。
  • 失败样本记入 rec 不中断（沿用 1.0.1 行为），调度器自动重试 1 次。
4

ANALYZE · 信源分析与引用洞察（整合 Answerbit）

🟢 M16 · 信源地图（新增）

  • 进/退出规律：跨周期聚合引用域名，识别"高频被引用 / 偶发 / 已消失"三类信源，形成信源地图——这是报告指出的"他人难以复制的数据资产与壁垒"。
  • 权威权重：引用域名与 benchmark.cn_domains 全国大盘对照，标注权威度，指导内容投放到高权域。
  • 主题分组：引用按问题主题聚类，定位"竞品优势主题"与"高引用内容机会主题"。

🟡 M5 · 分析升级（增强）

  • 分组趋势：原 per_engine/engines/quality 扩展为"按主题分组趋势视图"，用户可切主题看各平台变化。
  • 竞品并排：原生支持 cfp[] 竞品添加与并排对比（原系统已能采竞品，1.0.2 将其产品化为对照卡）。
  • 引用域名深度：在 citations 基础上增加"高引用域名 TopN / 来源文章摘要"面板。
5

OPTIMIZE · 内容优化引擎（整合 Answerbit）

🟢 M17 · 优化中心（新增）

  • 高引用范文参考：从 M16 信源地图选取高引用内容作模板，注入 generate 的 draft 提示，提升新内容被引用的潜质。
  • AI 文章生成：复用 M7 的 outline/draft/lint，新增"基于引用洞察生成"开关，自动带入高权域与竞品缺口。
  • 推荐发布渠道：生成后给出发布落点建议（复用 M10 PUBLISHERS），用户自行决定发文，不自动群发（保持 1.0.1 安全边界）。

🟡 M7 · 生成闭环验证（增强）

  • 发布后由 M15 调度器持续追踪该内容的"被引用/排名"变化，回到概览面板形成优化 → 验证闭环（对应 Answerbit OPTIMIZE 的"持续追踪指标变化"）。
  • verify.py 的 external.any 验收器与发布落点域名联动，自动判定内容是否进入 AI 信源池。

度量升级与合规中立

🟢 曝光效果综合分（新增）

  • 对齐 Answerbit 度量口径：曝光效果分数 = 品牌提及率 + 平均排名 + 引用质量 加权综合。
  • 权重可配（默认 提及率 0.4 / 排名 0.3 / 引用质量 0.3），输出单分便于跨品牌/跨周期横向对比。
  • 在概览面板新增"曝光效果分"卡片，历史序列由 M15 归档驱动。

🟢 M19 · 数据中立与合规适配（新增，对应报告补充板块 ②）

  • 第三方中立视角：强调不站队任何大模型，数据底座中立，与腾讯/阿里"监测路线"形成差异化（报告机会点 ⑥）。
  • 采集合规边界：模拟提问采集是否触线、AI 回答合规边界、品牌负面被放大责任归属——在采集层加合规开关与审计日志。
  • 数据资产沉淀：信源地图 + 监测历史作为客户可托管的独立数据资产，降低"无数据说话"续约风险（报告风险 ⑧）。
💡 与报告战略对齐：1.0.2 把"监测底座 → 数据化交付 → 策略与内容上移"的优先级落到产品上，直接回应报告三条实在建议与五大机会点。

🟢 9.3 多平台统一接入方案（Connector Adapter）

八平台均兼容 OpenAI Chat Completions 形态（文心需先换 token），因此采用适配器模式：一个抽象基类 + 各平台薄封装，对上暴露统一接口 ask(prompt, model) → {text, usage, raw}，对下屏蔽协议差异。监测调度器（M15）只依赖统一接口，不感知具体平台。

# connectors/connector.py —— 统一接入骨架（示意）
from abc import ABC, abstractmethod
class BaseConnector(ABC):
    name: str
    base_url: str
    models: list
    @abstractmethod
    def auth_headers(self) -> dict: ...
    @abstractmethod
    def chat(self, prompt: str, model: str, **kw) -> dict: ...

class BearerConnector(BaseConnector):           # 豆包/智谱/DeepSeek/Kimi/MiniMax/通义/元宝
    def auth_headers(self): return {"Authorization": f"Bearer {self.api_key}"}

class QianfanConnector(BaseConnector):          # 文心一言：OAuth2 换 token
    def auth_headers(self):
        self.ensure_token()                     # 缓存 access_token，到期前刷新
        return {"Authorization": f"Bearer {self.access_token}"}

# 统一请求/响应归一化：request 统一为 messages；response 统一抽取
# {content, prompt_tokens, completion_tokens, finish_reason, platform, model, latency_ms}
REGISTRY = {c.name: c for c in [Doubao, Zhipu, DeepSeek, Kimi, MiniMax, Qwen, Wenxin, Hunyuan]}

🟢 9.4 认证与密钥安全存储

  • 绝不硬编码：ApiKey/SecretKey 只存于密钥保管（环境变量、KMS、Vault 或加密配置文件），运行时注入，禁止写入代码仓库与日志明文。
  • 加密落盘：connectors.json 仅存连接参数，密钥单独存 secrets.enc（AES-GCM），进程启动用主密钥解密，主密钥来自环境变量。
  • 文心 token 托管：access_token 由连接器在内存缓存（有效期≈30 天），到期前 1 天自动用 SecretKey 刷新，刷新失败触发告警。
  • 最小权限与轮换：每家平台申请「仅推理」权限的 Key；支持多 Key 轮询，单 Key 泄露可秒级吊销不影响整体。
  • 审计：密钥读取/使用记入安全审计日志（M19 合规层），可追溯「哪个工作空间、何时、调了哪个平台」。

🟢 9.5 配额管理

  • 每平台配额配置：在 connectors.json 记录 rpm/tpm/daily_budget（Token 或金额），调度器据此限流，避免超额 429。
  • 计量（Metering）：每次调用累加 prompt_tokens + completion_tokens 与各平台账单口径，按工作空间分摊，对接 M18 配额看板。
  • 预算护栏：达日预算 80% 预警、100% 熔断该平台并切降级链；多 Key 场景按权重分摊 QPS。
  • 限速自适应：收到 429 时按 Retry-After 退避，并将该平台瞬时配额自动下调一档，恢复后再缓慢抬升（令牌桶）。

🟢 9.6 错误码处理建议

HTTP 码含义通用建议平台特异性提示
400请求体/参数错误校验模型标识是否在当前可用清单（旧名失效常见）、messages 结构、超长截断DeepSeek/Kimi 模型名改版即 400；MiniMax 命名大小写敏感
401认证失败检查 ApiKey 是否有效/过期；文心先确认 access_token 是否刷新文心 token 过期；密钥被吊销
403无权限确认 Key 具备推理权限、模型是否在申请范围、地域是否开通部分模型需单独申请（如百炼 MiniMax）
404端点/模型不存在核对 base_url 路径与模型标识；勿多带 /v1 或填官网首页Kimi/MiniMax 端点拼错高频
429触发限速/配额读 Retry-After 退避；下调该平台配额；计入预算护栏全局限流，勿盲重试
500/502/503服务端错误/过载指数退避重试（≤3 次）；仍失败则走降级链换平台高峰期常见，属可降级错误
超时网络/推理慢设合理 timeout（建议 30–60s）；超时可重试（幂等提问类）reasoner/长上下文更易超时
💡 处理分层：可重试（429/500/503/超时，带退避）→ 可降级（服务端错换平台）→ 需告警人工（401/403 密钥或权限问题，立即通知负责人）。

🟢 9.7 降级与容灾策略

  • 平台降级链（Fallback Chain）：为每个监测任务配置候选平台顺序，例如 deepseek-chat → qwen-plus → hunyuan-turbo → glm-4.5-flash；主平台连续失败 N 次即切下一候选，保障「采样不中断」。
  • 熔断（Circuit Breaker）：单平台错误率超阈值（如 50%/1min）临时熔断，冷却期内请求直接跳至降级链，避免雪崩与无效配额消耗。
  • 重试与退避：仅对可重试错误重试，采用指数退避 + 抖动（1s→2s→4s，上限 3 次），配合 Retry-After。
  • 结果一致性：监测提问为「是否提及品牌 X」的判定类任务，跨平台结果可合并为「多模型共识度」，单平台缺失不影响整体指标，反而提升鲁棒性。
  • 本地缓存：同提问短时（如 10min）命中缓存，降低对不稳定平台的依赖；geo.json.monitor 可配置缓存 TTL。
