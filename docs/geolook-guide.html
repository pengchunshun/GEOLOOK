GEOLOOK 是一套面向"星火之光生成式引擎优化（GEO）"的可运行方法论：它把抽象的"让 AI 更懂你的品牌"拆解成一组可被抓取、计算、验收、交付的工程动作。所有评分口径并非拍脑袋，而是来自 references/ 中记录的实测数据（如 CNN/GEO、CN-GEO 论文与 citation-lab 实证数字）。

工具提供两条使用路径：可视化看板（dashboard.py，适合客户演示与团队协作）与命令行（geo.py，适合自动化与批量处理）。两者共享同一套 scripts/ 业务逻辑，产出统一存放在 work/<slug>/ 工作区。

01项目架构说明

GEOLOOK 采用"薄入口 + 厚逻辑 + 单一真相源"的分层结构。所有命令都经 geo.py 分发，业务逻辑在独立模块中，执行状态集中在 work/<slug>/tasks.json。

① 入口层

命令分发与交互
  • geo.py — CLI 主入口
  • dashboard.py — Web 看板（Flask）
  • doctor.py — 环境自检
  • webui.py — 看板后端 API

② 逻辑层

核心业务能力
  • audit.py — 体检评分
  • sample.py — 答案采样
  • tasks.py — 工单生成
  • generate.py — 资产生成
  • verify.py — 自动验收
  • report.py / deliver.py

③ 支撑层

基础设施
  • geolib.py — 公共库 / 抓取 / 配置
  • fcntl.py — Windows 文件锁兼容
  • config.py — 配置加载
  • fetch.py — 抓取器
  • tests/ — 单元与回归测试

工作区产物（work/<slug>/）

路径含义

设计要点：tasks.json 是"执行状态的唯一真相源"。plan 生成工单、generate 回写资产路径、verify 回写验收状态——三阶段都围绕同一份文件读写，避免多份状态互相打架。

02核心模块功能介绍

每个模块职责单一、可独立运行，通过 geolib 公共库共享抓取与配置能力。

audit

audit.py

页面 GEO 体检。把 citation-lab 实证结论变成可计算分数：长度（Top 四分位 1,943 词 vs Bottom 170 词）、结构（标题/段落/列表密度）、抽取块（数字 +61.6%、定义 +57.3%、对比 +55.3%、how-to +41.2%）、对题性（llm_relevance_score，r=0.432 最强预测因子）。

sample

sample.py

AI 答案采样。把问题库打到各引擎量化"品牌在 AI 答案里的可见性"。三种模式：api（有 API 直跑）、browser（网页端由 Claude 逐条采）、manual（人工粘贴）。关键口径：Web ≠ App，分平台分终端单独记，绝不混算。

tasks

tasks.py

工单系统。把诊断变成分派/验收/追踪的执行任务。每条工单必须含：依据（追到 method.md 哪条）、负责角色、验收标准、市场。无验收标准的不叫工单叫愿望。内置风险分级（low/watch/high）。

generate

generate.py

资产生成器。产出到 assets/，中英分开：llms.txt、JSON-LD、定义/FAQ 片段、内容大纲、可选 LLM 初稿。分工原则：结构性资产由代码确定性生成（不漏字段、不写错格式）；正文由 LLM 按大纲写（代码写不出好文案）。

verify

verify.py

验收闭环。重抓站点 → 跑 checker → 回写 tasks.json 状态。"建议"与"服务"的分界：能自动验收的，不靠人说做完了。支持 site./pages./metrics./external. 四类共 20+ 种校验规则。

report/deliver

report.py / deliver.py

报告与交付。把一期产出打成可直接发客户的目录：总览 HTML、诊断报告、30/60/90 执行方案、工单表、验收表、资产包。面向客户故不出现内部脚本名，每个结论写清依据，不承诺任何平台必然引用。

验收规则语法（verify）

类别示例规则含义
site.site.no_ai_bot_blockrobots 不再整站封 AI 抓取器
site.site.llms_txt_validllms.txt 抽样链接全部有效且未被封
site.site.avg_score_gte:70重跑 audit 均分达标
pages.pages.has_jsonld受影响页面已挂 JSON-LD
pages.pages.block:定义缺该抽取块的页面数下降 ≥50%
metrics.metrics.mention_rate_gte:cn:0.3指定市场平均无提示提及率达标
external.external.any:a.com,b.com采样里出现任一目标域名的引用
相对型指标（如"下降 50%"）用工单的 baseline_count（生成工单时的真实缺口数）做基线，而非凭空设定目标。这是验收可信的关键。

03设计理念与实现逻辑

GEOLOOK 的底层信念：GEO 不是玄学，是一组可被度量、可被工程化、可被验收的"可见性动作"。

① 实证驱动，拒绝拍脑袋

所有评分阈值与权重来自 references/method.md 的实测数字。例如长度项直接采用 Top/Bottom 四分位的词数差异倍数；对题性用 llm_relevance_score 的相关系数（r=0.432）作为最强预测因子加权。规则与数据可回溯，结论可辩护。

② 代码确定性 vs 人写文案

结构性资产（llms.txt、JSON-LD、HTML 片段）由代码生成，保证不漏 schema 字段、不写错格式；文章正文交给 LLM 按大纲写，代码不越俎代庖写文案。生成器（generate.py）明确划分"机器做"与"人做"的边界。

③ 单一真相源 + 自动验收

tasks.json 是执行状态唯一来源，verify 不修改内容只重抓判定，把"建议"升级为"服务"。能自动验收的，就不靠人报"做完了"。

④ 风险分级与保护性纪律

优先级说"多重要"，风险说"动手多小心"，二者独立。解封 robots 是 P0 也是高风险（错一行封全站），执行顺序按"先低风险、高风险单独排期并留回滚"（见 method.md 保护性纪律）。

关键工程取舍

  • 跨平台兼容：fcntl.py 是 Windows 文件锁兼容层（基于 msvcrt），使原本依赖 Unix fcntl 的代码可在 Windows 原生运行，无需 WSL。
  • 平台隔离：sample.py 的 PROVIDERS 注册表区分 cn / en 市场与观测集合；Web 与 App 答案分终端单独记录，避免混算失真。
  • 三语安全：抽取块正则同时覆盖中 / 英 / 日表述，否则会把日文页整体误判为"缺块"；"如何/怎么"等弱信号必须配合列表结构才计为操作步骤块，防止问句标题刷分。
  • 功能页豁免：登录 / 注册 / 购物车 / 联系页等天然低内容，不按 SPA 空壳 P0 误报（FUNC_PAGE 正则）。
  • 最小检索单元：按 H2 把正文切成段落组——一段能独立回答问题的文字可赢过竞品整页（GEO Readiness Manual）。

04典型应用场景

场景 A

出海品牌的双语 GEO

配置 market: both，audit 与 sample 双市场并行，generate 自动产出 llms.txt 与 llms.en.txt；verify 用 site.lang_balance / site.en_pages_gte 验收中英文页面均衡度。

场景 B

SaaS 产品的可引用性改造

audit 识别"缺数字/定义/对比/FAQ 块"的页面，generate 产出 definition/faq 片段与 JSON-LD，verify 用 pages.block:* 验收抽取块补齐。

场景 C

AI 爬虫被误封的恢复

audit 报 site.no_ai_bot_block / site.no_ai_ua_block，plan 生成高风险工单，verify 重抓确认 robots 放行——典型"P0 + 高风险"排期。

场景 D

代理机构批量客户交付

每客户一个 slug，dashboard 切换项目；deliver 输出客户友好的 HTML/CSV 包，不暴露内部脚本名，结论附依据。

场景 E

竞品可见性基准对比

config 配置 competitors，sample 量化自身与竞品在各引擎的提及/引用率，metrics.own_cite_gte 跟踪官网被引用占比。

场景 F

持续监测闭环

周期性重跑 sample → verify，用 external.any 与 metrics.* 监控外站引用与品牌提及趋势，形成月度/季度报告。

05使用建议

① 启动与运行

  • 看板方式（推荐客户演示 / 团队协作）：
    python scripts/geo.py ui → 浏览器打开 http://127.0.0.1:8765/
  • 命令行方式（推荐自动化 / 批量）：直接调用 geo.py <command>
  • Windows 用户无需 WSL：脚本自带 fcntl 兼容层。运行时确保 scripts/ 在 PYTHONPATH 中（本地 fcntl.py 优先于系统模块被导入）。
  • 启动前先跑 python scripts/geo.py doctor 自检依赖、API Key、浏览器是否就绪，避免中途中断。

② 标准操作流程

# 1) 建项目并填写事实卡（最关键的一步）
python scripts/geo.py init   # 按提示填 facts.md

# 2) 体检 + 采样（可并行）
python scripts/geo.py audit
python scripts/geo.py sample

# 3) 生成工单 → 产出资产 → 自动验收
python scripts/geo.py plan
python scripts/geo.py generate
python scripts/geo.py verify

# 4) 交付
python scripts/geo.py deliver
事实卡是第一生产力。content/facts.md 是评分与资产生成的唯一事实源。定义一句话、关键数字表、适用/不适用场景填得越准，下游 llms.txt 与 JSON-LD 质量越高。务必先把它写扎实。

③ 工单执行纪律

  • 优先级 ≠ 风险：按"先低风险快速优化，高风险技术改造单独排期并留回滚"的顺序推进。
  • 没有验收标准的不接：工单必须有可校验的 acceptance.check，否则是愿望不是任务。
  • watch 类任务看窗口：改已有页面内容后，按 7 / 14 / 28 天观察窗看真实数据再判定。

④ 避坑清单

不要做

  • 不要混算不同平台 / 终端的采样结果
  • 不要把"建议"当"已交付"——以 verify 结果为界
  • 不要在没回滚预案时动 robots / WAF / noindex
  • 不要向客户承诺"某平台一定引用"

应该做

  • 先 doctor 自检再开跑
  • 把事实卡 / 工单 / 资产统一收进一个 slug
  • 结构性资产用 generate 确定性产出
  • 周期性 sample → verify 形成监测闭环
依赖说明：部分模块（sample / generate 调用的 LLM）需要 requests / bs4 / lxml 与对应平台 API Key（如 ZHIPUAI_API_KEY、ARK_API_KEY）。缺失 API Key 时，相关平台自动降级为 manual 采样，不会中断整期。
