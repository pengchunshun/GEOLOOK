产品定位与核心价值

一、GEO 是什么

GEO（Generative Engine Optimization，生成式引擎优化）是 SEO 之后的新范式：SEO 让品牌在搜索结果里排名靠前，GEO 让品牌在 DeepSeek、豆包、元宝、Kimi、千问、ChatGPT、Gemini 等大模型回答中被推荐与引用。当品牌在 AI 回答中缺席，就等于在决策链上缺席。

二、星火之光解决什么问题

  • 可见度黑盒 → 可量化：自动模拟真实用户提问，采集各 AI 平台对品牌的回答，把"被提到几次 / 排第几 / 引用了谁"变成结构化数据。
  • 优化建议可落地：基于采样与站点体检，生成可执行的站点改造、内容生产与发布计划。
  • 交付可签收：诊断报告、优化方案、执行方案三份正式文档，形成对客户可续约的数据化交付物。
  • 中立、本地优先：数据底座中立、不站队任何大模型；运行于本地，凭证仅存项目根 .env。

三、目标用户

GEO 服务商

代运营 / 咨询团队

批量管理多客户品牌的 AI 可见度，用数据化交付物支撑续约。

品牌方市场部

品牌 / 增长团队

持续监控自家与竞品在 AI 回答中的表现，指导内容投放方向。

独立站 / 出海

站长 / 创业者

用 llms.txt、JSON-LD、FAQ 等结构化资产提升被 AI 引用的概率。

💡 设计原则（贯穿全系统）：① 监测底座优先于执行；② 交付物数据化；③ 内容策略上移、底层执行可自动化；④ 不替用户自动发布，发布只由明确点击/命令触发。

系统架构总览

一、技术栈

  • 语言：Python 3.11+（仅依赖 requests / bs4 / lxml，零商业 SDK，无 GPU 需求）。
  • 前端：单文件 ui.html（原生 JS + 内联 SVG 图表，无构建步骤、无前端依赖）。
  • 后端：Python 标准库 http.server 自托管仪表盘；首启动用 fcntl 文件锁保证单实例。
  • 存储：每个项目一个目录 work/<slug>/，纯 JSON + JSONL，无数据库。
  • 大模型调用：通过 OpenAI 兼容 / 火山方舟 / 腾讯云等协议直连各厂 API，Key 存 .env。

接入层 ui.html（单页仪表盘） ──HTTP──▶ dashboard.py（http.server + /api/*）

引擎层 sample.py · PROVIDERS（20+ 平台 + 新增 3 国产引擎）· ask()（统一调用层）

功能模块详设

M1 · 项目与工作流（geo.py / 接入引导）

  • CLI：python3 scripts/geo.py init 创建项目；serve 启动仪表盘；run <action> 单步执行；autopilot 一键跑全流程。
  • 接入引导（onboard）：三步向导——填品牌/官网 → 配引擎 Key（至少 1 个）→ 自动采样并生成交付物，无 Key 也能创建（仅抓站+体检）。
  • 默认平台：DEFAULT_PLATFORMS 按市场预置采样平台（cn / global / both）。

M2 · 站点抓取与证据（crawl.py）

  • 站点级信号：robots、sitemap（最多跟 8 个分片，防拖死）、llms.txt 探测。
  • 代表性页面：按 PRIORITY 关键词（product/pricing/案例/文档/FAQ/产品/方案…）优先抓取正文。
  • 产物：evidence/site.json（站点级）、evidence/pages.jsonl（每页正文+结构+JSON-LD）、evidence/html/（原始快照供复核）。

M3 · 页面 GEO 体检（audit.py）

  • 评分口径来自 references/method.md 实测数字（非拍脑袋）：长度（Top/Bottom 四分位 11.4x）、结构（标题/段落/列表密度）、抽取块（含数字 +61.6%、定义 +57.3%、对比 +55.3%、how-to +41.2%）、对题性（llm_relevance_score，最强预测因子 r=0.432）。
  • 三语判块（中/英/日）避免误判；功能页（登录/购物车等）不按 SPA 空壳误报。
  • 产物：audit.json，输出站点 GEO 健康度分数。

M4 · AI 答案采样引擎（sample.py）

  • PROVIDERS 注册表：覆盖 20+ 平台，含 API 引擎（DeepSeek、智谱 GLM、豆包、Kimi、MiniMax、通义千问（百炼）、文心一言（千帆）、腾讯元宝（混元）、OpenAI、Gemini、Claude、Grok、Perplexity 等）与人工平台（纳米 AI/百度/微信搜一搜）。
  • ask() 统一调用层：OpenAI 兼容 / 火山方舟(ark) / 腾讯云(anthropic) 协议；自动解析引用 search_info。
  • 采样：逐平台问"在推荐品类时是否提及品牌"，记录 answer / citations / refs / model；失败记入 rec 不中断。
  • 底层 LLM（LLM_PREFS）：bootstrap/expand/generate 等任务自动挑选有 Key 的引擎驱动。

M5 · 采样分析与指标体系（sample.analyze / benchmark.py）

  • per_engine：每引擎的回答数、提及率、平均排名、引用域名数。
  • engines：引擎表现汇总（提及率/排名/引用质量分布）。
  • quality：语料质量（长度/结构/抽取块密度）。
  • benchmark：引用域名与全国大盘（cn_domains.json）对照，识别高权威信源。

M6 · 问题库推导（bootstrap.py / expand.py）

  • bootstrap：从品牌事实（about/audience/goals）用 LLM 推导初始问题集。
  • expand：调用百度/Google 搜索建议（suggest_baidu/suggest_google）扩展真实用户问法，分类（定义/对比/购买/排查/教程）。

M7 · 内容生成（generate.py）

  • 结构化资产：llms.txt（面向 AI 的站点说明）、JSON-LD（Organization/FAQ/HowTo 等 Schema）、FAQ 块、定义块。
  • 大纲与成稿：按问题生成文章大纲与正文草稿（可指定 provider）。
  • 自检：lint_draft 检查草稿是否覆盖要点、是否被 AI 友好结构化。

M8 · 验收验证（verify.py）

  • 逐项检查工单是否达成：external.any 检查器可用发布落点域名做"已被引擎引用"判定，闭环到验收。
  • 产物：verify_report，输出每任务通过/未通过/证据。

M9 · 内容蓝图（blueprint.py）

  • 汇总待建内容地图：缺哪些页面/资产、优先级、与现有内容的关系（existing_content）。

M10 · 发布渠道（publish.py）

  • 渠道注册表 PUBLISHERS：GitHub（提交 md）、WordPress（建草稿）、Webhook（打到自建接收端）。
  • 安全边界：凭证仅存 .env；只建草稿/提交文件，无自动群发；微博/小红书/头条等无公开 API 平台不接入（走人工或 Webhook）。
  • 产物：publish.json 发布记录，供验收引用判定。

M11 · 交付物与报告（deliverables.py / report.py / deliver.py）

  • 诊断报告：现在什么样——站点体检 + AI 可见性 + 全国大盘对照。
  • 优化方案：应该改成什么样——结论、机会地图、建设地图、资源取舍。
  • 执行方案：谁在何时做什么——工单、排期、验收标准、资产清单。
  • 三份均出 Markdown + 自包含 HTML，供客户签收与续约。

M12 · 引擎与密钥管理（dashboard + PROVIDERS）

  • GET /api/keys 返回所有引擎配置状态（已配/未配、模型、尾号）。
  • POST /api/keys 写入 .env（仅允许 PROVIDERS 推导出的变量，防越权）。
  • 测试连接：POST /api/keys/test 临时注入 Key 真实打一次，返回模型实测回复，配前即可验证可用（不写文件）。
  • 设置页"引擎与密钥"卡片动态遍历 PROVIDERS，按"已配优先/联网优先"排序，给出建议配置。

M13 · 作业与任务（jobs.py / tasks.py）

  • jobs.start/stop/tail：各动作（sample/serve/autopilot）异步作业，前端实时日志。
  • tasks：工单状态机（todo/doing/done/blocked/wontfix），驱动执行方案。
  • 孤儿作业回收 reap_orphans。

M14 · 仪表盘与 UI（dashboard.py + ui.html）

  • 视图：概览（可见度打分）、项目、采样表（API/人工平台指令）、引擎表现、看板、设置（品牌/引擎与密钥/通用）。
  • 接入引导 onboard、onboard_over 覆盖向导；手动采样表可复制指令到各平台。
  • 内联 SVG 图表：可见度趋势、引擎对比、引用域名分布。

度量指标体系

系统已内置的可见度度量（1.0.1 基线），是后续与 Answerbit 综合分对齐的基础：

指标定义口径
提及率品牌在回答中被提及的比例per_engine 回答中提及品牌数 / 总回答数
平均排名品牌在推荐列表中的位次回答中品牌出现位置均值（越靠前越好）
引用质量AI 引用了哪些信源citations 数量、域名权威度（benchmark 对照）
语料质量站点自身可被引用的潜质长度/结构/抽取块密度（audit）

部署与运行

# 1. 安装依赖
pip3 install requests beautifulsoup4 lxml

# 2. 启动仪表盘（本地优先，默认 http://127.0.0.1:8765）
python3 scripts/geo.py ui

# 3. 命令行单步
python3 scripts/geo.py init      # 创建项目
python3 scripts/geo.py run sample # 采样
python3 scripts/geo.py run autopilot # 全流程

# 4. 配置引擎 Key（界面设置 → 引擎与密钥，或手动写 .env）
# 例：DASHSCOPE_API_KEY / QIANFAN_API_KEY / HUNYUAN_API_KEY
🔒 数据安全：所有凭证仅存项目根 .env（已 gitignore）；采样与发布均不离开本地控制；发布动作只由明确点击/命令触发。

当前能力边界（1.0.1 基线）

手动触发

采样为按需/一键

尚无"天级自动并行调度"；采样由用户点击或 CLI 触发，未形成持续监测节奏。

单品牌

工作空间缺失

当前以单项目（单品牌）为主，多品牌/多团队/权限配额管理尚未体系化。

趋势分组弱

信源地图未产品化

引用域名分析已有，但"按主题分组趋势 / 信源进退出地图"未作为独立模块呈现。

已具备

优化闭环雏形

采样→分析→生成→发布→验收→三报告已闭环，是整合竞品能力的高地基。
